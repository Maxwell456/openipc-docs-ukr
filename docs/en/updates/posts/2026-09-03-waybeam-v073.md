# Waybeam v0.73 — a third chip, NPU detection, on-board QR and slices

Seven weeks after [July's v0.40](/en/updates/posts/2026-07-11-waybeam-v040) — and this is the largest leap in the project's history: **33 minor versions, around 250 commits**. The current version is **v0.73.3**, the HTTP API contract **0.22.0**.

The headline in one paragraph: Waybeam stopped being "an encoder for SigmaStar" — a third backend now runs on **HiSilicon CV610**. The camera learned to recognise objects on its built-in NPU and to read QR markers by itself. The stream can be sliced so that a lost packet no longer kills a whole frame. And a new transport hands whole frames to shared memory, bypassing RTP entirely.

---

### ⚠️ The repository was renamed <Badge type="danger" text="BREAKING" />

`OpenIPC/waybeam_venc` → **[`OpenIPC/waybeam`](https://github.com/OpenIPC/waybeam)**.

GitHub redirects the old URL, so existing clones, forks and remotes keep working without a change. The product, binary, `/etc/waybeam.json` config, init script and release tarball are all named simply `waybeam` now. The old name still appears in historical documents, source comments, the dashboard's page title and the exported config filename — but no longer in the URL.

### 🔹 CV610 — a third chip, and not a SigmaStar one

The biggest structural change. **v0.65.0** (13 August) introduced the `SOC_BUILD=cv610` backend — **HiSilicon Hi3516CV610 with the Sony IMX662 sensor**. The whole of August went into bringing it to parity.

What already works:

- the MIPI → VI → ISP → H.265 VENC graph in VI-online mode; full-frame **1080p30/60** (RAW12) and **1080p90/100** (RAW10). Confirmed on hardware at ~99 fps
- RTP over UDP and abstract UNIX sockets, plus `frame-shm://` — which is the **default output** on this chip
- audio: inner ACODEC → AI → Opus 48 kHz mono, 10 ms, 32 kbit/s (~100 access units/s with zero send drops)
- **IQ tuning**: 11 ISP groups, 59 fields — saturation, color_tone, noise reduction, sharpen, gamma, exposure. The dashboard's IQ tab is now driven by the capability feed rather than a hardcoded condition, so it is no longer hidden on CV610
- `sensor.index` / `sensor.mode`, `isp.keepAspect`, `video0.size` (via VPSS), QP bounds, the debug OSD, `/api/v1/awb`, `/api/v1/audio/status`, `/api/v1/snapshot.jpg`
- resilience presets and `video0.sliceCount`; intra-refresh **by column** (v0.68.0) — so the GDR recovery frame keeps its slices
- SD recording in `mirror` mode, format `ts` with Opus muxed in (v0.70.0)

::: warning Not on CV610 yet
Stabilization and digital zoom (`video0.framing`), object detection, QR and attitude. `video0.qpDelta` was **removed** in v0.73.0 — CV610's CBR controller stores the value but never acts on it; `video0.intraRefreshQp` replaces it there. `record.mode: "dual"` needs a second VENC channel it does not have, so the request is refused with a warning. `/api/v1/iq/import` answers `501`.
:::

**The CV610 default config** is `1280x720@100` at 2600 kbps (v0.65.3 dropped it from 8000: the consumer here is waybeam-link, not a browser).

::: danger Never unload MPP modules under a live consumer
On CV610 MPP objects are kernel state and survive a process crash. **v0.65.10** removed both paths that did it: the `S95waybeam reload` action and the module rollback on a failed start. Either could wedge the SoC. The correct post-crash recovery is a plain `restart`.

Two more findings established by measurement: the `MMB LEAK` lines in the log are **the kernel reclaiming**, not losing; and a `SIGKILL` leaves behind ISP state rather than VB, plus two stranded `aenc` blocks — which is exactly why audio silently failed to come back after a crash. Since v0.65.9 the audio module is cycled before bring-up and sound recovers on its own.
:::

### 🔹 NPU object detection <Badge type="tip" text="Star6E + Maruko" />

An entirely new subsystem (v0.48.0). The detector runs on the camera's **idle IPU/NPU**, and the result is streamed as per-frame metadata.

The architecture is **pluggable**: waybeam owns the model-input-size frame tap, the reader thread, the config and the carriers; a `.so` plugin owns the IPU device and the decode. So **a new model is a config change, not a waybeam rebuild**. Everything model-specific — models, decode, class tables — lives outside this repository.

Where the result goes:

- **a DETECT trailer in the RTP sidecar** (flag `0x10`): a 16-byte header plus a TLV body with normalized-u16 boxes. It is attached to **every** frame while a subscriber is present, so the data survives RF loss
- **boxes on the debug OSD** — palette colors per class plus a `det N` row; snapshots older than 700 ms are not drawn

How it developed over six weeks:

| Version | What arrived |
| :--- | :--- |
| v0.48.0 | the subsystem itself, the plugin boundary, the DETECT trailer, OSD boxes, a Detection section in the WebUI |
| v0.51.0 | `confThresh` / `nmsIou` finally reach the plugin (the host used to pass zeros, so every backend ran its built-in `0.40`/`0.45`), configurable tap geometry `netWidth`/`netHeight` replacing the hardcoded `640×352`, and `modelId` |
| v0.52.0 | **hot model swap** — no pipeline respawn, no dropped stream |
| v0.53.0 | `detect.enabled` became **live** |
| contract 0.15.0 | parity with **Maruko** (detector on SCL port 3) |

::: info Why the threshold should default to ~0.20
`0.40` is too high for small objects: INT8 quantization costs roughly **30% of the score** compared to FP32 precisely on them. The intended architecture is to run the detector at ~`0.20` and let the ground tracker reject noise with its 2-hit confirmation.
:::

::: warning Detection and stabilization are mutually exclusive
Both claim the same tap (VPE port1 on Star6E, SCL port3 on Maruko). There is no detection on CV610.
:::

→ The subsystem now has a **page of its own**: [**NPU object detection**](/en/software/waybeam-detection) — every `detect` field, the DETECT trailer format, tap geometry, why `modelId` cannot be derived, and the full story of how `detect.enabled` became live.

### 🔹 On-board QR scanning <Badge type="tip" text="Star6E" />

The camera decodes a QR marker out of its own frame — no laptop in the loop. New endpoints: `GET /api/v1/qr/scan[?ms=N]` (a window that closes itself once a code is found), `/qr/stop`, `/qr/status`, `/qr/tap.pgm`.

Only a locked envelope is accepted: QR Version 1 (21×21), error correction Q, exactly **16** alphanumeric characters, the first one a type of `P` or `C`. Plus a mandatory continuous black frame around it (a 33×33-unit marker) — that border is what supplies four stable projective corners, which is why the production decoder **never** runs unbounded finder-pattern discovery. Measured across 768 generated 1280×720 symbols: the frame was identified in 100% of cases and the payload decoded in **92.3%**, against 65.9% for stock quirc.

The key detail is an **overlay-free** luma tap (`qr.tapEnabled`, `tapWidth`, `tapHeight`): an OSD drawn over the marker would break recognition. The decode is isolated in the external `/usr/bin/qr_decode`, which now **reads JPEG natively** and is built with `-O3` — 1.66× faster end-to-end.

::: danger Pairing itself is not implemented yet
Waybeam ships **only the transport layer**: the marker geometry, envelope validation and decoding. It returns 16 characters and stops — it **does not interpret, authorize, persist or execute** that payload.

The `P` and `C` prefixes **reserve** transport types for future pairing/passphrase and command/settings logic, but their meanings and the structure of the remaining 15 characters are **deliberately not implemented**. Pairing, commands, boot scheduling and action dispatch are deliberately kept outside the waybeam binary, in a separate work package that exists neither in the repository nor in the release yet.
:::

::: danger `/api/v1/snapshot.pgm` was removed — and this was not housekeeping
The old grayscale PGM snapshot the QR decoder used now returns **404**. Its per-request VPE/SCL tap **could kill the SoC**: device-verified as `DisablePort … mhal not return buffer`, followed by an `EnsureInputPortFifoEmpty` storm.

The MJPEG channel has no such cycle — it is created once at pipeline start. So QR now consumes the ordinary `/api/v1/snapshot.jpg`. The error codes `bad_crop`, `bad_max_dim`, `snapshot_gray_busy` and `snapshot_gray_unsupported` went with it.
:::

→ QR has a **page of its own** too: [**On-board QR scanning**](/en/software/waybeam-qr) — the full marker-format table, the pixels-per-module budget, generating markers, all API responses and the port1 claimant priorities.

### 🔹 Multi-slice H.265 — `video0.sliceCount`

The picture is split into several **independent** slices (1..32, restart). The point is spatial concealment: when RF loss goes past the FEC budget, it costs a **frozen region** instead of the whole frame.

On Star6E (v0.66.0) this meant binding `MI_VENC_SetH265SliceSplit` — a symbol the shipped library had exported all along and nobody had ever wired. CV610 and Maruko followed in v0.67.0.

Device-verified: on CV610 (1080p30/60/100) requests 1, 3, 4, 6, 9, 12 and 17 delivered exact VCL-NAL counts; on Maruko at 720p30, 1, 4 and 12 were exact while 17 and 32 quantized to the picture maximum of 12. If several slices are explicitly requested and the ABI cannot be applied or read back, **startup fails** rather than silently shipping a single-slice stream.

### 🔹 A new resilience preset: `ltr`

`video0.resilience = "ltr"` / `"ltr:<N>"` (v0.64.0) selects the most resilient reference structure this SoC can express: `InRnRnRn…`, **half the frames non-referenced**, so half of all frame losses cost exactly one frame instead of cascading to the next IDR. Unlike `rally` (same ratio), `ltr` **preserves your `gopSize`** and forces intra-refresh off — so it pairs with a long GOP and asymmetric FEC: heavy protection on the IDR, light on the rest.

The semantics of `u32Enhance` had to be established **by measurement** — the SDK documents nothing. It turned out to be a **period**: exactly one frame in every `enhance + 1` is emitted non-referenced. `enhance=1` → 50.0% droppable, `4` → 17.6%, `299` → 0.3%. So **smaller is more resilient**.

Measured bitrate cost at pinned QP 30 on a moving scene: **under 1%**.

::: info What else the measurement established
P-frames **always** predict from the previous frame, never from the IDR, and `bEnablePred` is a **no-op** for non-reference marking. The full SigmaStar SDK exposes no long-term-reference, SmartP or GOP-mode API, so an IDR-anchored ("virtual IDR") structure is not achievable on Infinity6E.
:::

One more detail: an unknown `resilience` value now returns **409**. It previously returned **200**, persisted to the config, and left the derived fields holding the **previous** preset's expansion — so `/api/v1/config` disagreed with the running encoder until the next start.

### 🔹 The `frame-shm://` transport — whole frames over shared memory

This transport (v0.42.0) carries **whole encoded frames** over POSIX shared memory, bypassing RTP packetization entirely: the consumer (waybeam-link) applies its own framing and FEC at **frame** boundaries.

The ring is SPSC lock-free, 8 slots × 384 KiB. Every frame carries metadata the transport can build asymmetric FEC from: the **GDR**, **ENHANCE** and **SALVAGED** flags plus its position in the intra-refresh cycle (`gdr_pos` / `gdr_len`).

::: danger The ring header is version 2 — rebuild the ground side <Badge type="danger" text="BREAKING" />
In **v0.69.0** offset 88 changed meaning: it carried `throttle_permille` (healthy value `1000`) and now carries `low_water_slots` (healthy `<= 1`) — **the polarity is inverted**. This is a deliberate hard break: every consumer validates `version` and **refuses to attach** on a mismatch rather than silently misreading the field.

A v2 producer **will not serve a v1 consumer**: `waybeam-link`, `waybeam-hub` and `radeon-vrx` must be rebuilt alongside the camera.
:::

### 🔹 SD recording no longer stalls the live stream

Before v0.70 **every backend called the recorder straight from the encode loop** — a `write()` to the SD card stalled the live video path. The writer now runs on **its own thread** on all three backends.

What else was fixed in v0.70–v0.73.3:

- rotation by `record.maxSeconds` / `maxMB` was **inert on a GDR craft** — a GDR stream has no natural IDRs, and rotation now asks for its own IRAP
- `/record/status` no longer races the writer thread — it is a coherent snapshot
- a mid-run `record/stop` can no longer stall live video
- `record.mode=dual` on Maruko no longer smashes its own thread stack, nor forces a keyframe into the **live** stream
- `droppedFrames` and `writerPeakDepth` are now **per-recording, not per-process**: the writer used to outlive any one recording, so a clean recording reported the previous one's drops
- `/record/status` gained `elapsed_ms`
- recording reached **CV610** (`mirror`, `ts` with Opus)

### 🔹 Rate control: QP bounds, `qpDelta` and fewer IDRs

- **`video0.minQp` / `maxQp`** — live QP bounds: Star6E since v0.64, CV610 since v0.65.6, **Maruko since v0.73.0**
- **`video0.qpDelta` was silently reverted at startup** (#255): applied from venc's own startup path it **logged success without reaching the encoder**. Fixed
- **the `qpDelta` default is now `-12`** on both SigmaStar backends (was `0`) — to bound the cost of an IDR
- on Star6E a `minQp > maxQp` request is now **rejected** instead of being written silently

::: tip Rate-control writes no longer force an IDR
`video0.bitrate` and `qpDelta` no longer request one after applying. Measured on an SSC338Q: ten live writes spaced 300 ms, counted as IRAP access units in the bitstream itself — `qpDelta` fell from 11 IDRs to 1.

The practical effect on the ground side: a bitrate write no longer consumes the shared 100 ms IDR gate, so a genuine recovery request arriving inside that window is no longer swallowed. Bootstrap IDRs (output enable, destination change, fps rebind, recorder start) bypass the gate unconditionally.
:::

### 🔹 Volatile writes: `GET /api/v1/live/set`

A new endpoint (v0.50.0) with the same field surface as `/set`, but **without writing to flash**. Built for high-cadence automated writers — waybeam-link's adaptive bitrate. Persisting at controller cadence is bad twice over: it wears the flash, and the camera reboots into the last adaptive transient.

Live fields only: a restart-class field answers `400`, because a pipeline reinit reloads from disk and would silently discard the value. Builds without the endpoint answer `404` — clients probe once and fall back to `/set`.

### 🔹 What was removed — check your configs <Badge type="danger" text="BREAKING" />

Three fields are gone. The shared rule: **a config carrying them still loads** (unknown keys are ignored and disappear on the next config write), but `/api/v1/set` or `/api/v1/live/set` naming them **fails the whole request** with `404 unknown config field`. If your ground station has a saved "apply my profile" batch, strip them from it.

**`video0.maxIBytes` / `maxPBytes`** (lived v0.45–v0.71, removed in v0.72.0). Measurement on an SSC338Q (720p60, H.265 CBR, GDR) showed they do not impose the ceiling they name: across `maxPBytes` 33144 → 6000 bytes the delivered rate moved under **0.3%**, and an access-unit census found **all 863 units over the cap** (mean 40247 B). The replacement for I-frame size is `video0.qpDelta` (a 68× range on the same rig, and it does not keyframe); for P-frame size there is no direct replacement, leaving `minQp`.

**`outgoing.shmThrottle`** (lived v0.57–v0.68, removed in v0.69.0) together with the clamp mechanism itself. On a `frame-shm://` craft the rate controller is co-located, already reads the same ring, and already owns `video0.bitrate` — the clamp was a second controller on the same signal, and its only actuator keyframes. Measured on a Star6E at 720p120: clamp on, 6.5 IDR/s and 100–143 ms glass-to-glass; clamp off, **0.2 IDR/s and 15–37 ms**. The same release removed the ring-full recovery IDR: it fired precisely when the largest frame could not be delivered anyway.

**`isp.aeEngine: "custom"`** (removed in v0.47.0). It turned out the `cus3a` thread never did AE convergence — the ISP firmware/bin AE always drove it, in both modes. Only `"sdk"` is accepted now; an old config carrying `"custom"` loads with a warning and falls back. The supervisory thread stayed on, as a limits enforcer.

### 🔹 Exposure: floors, ceilings and the 180° rule

- **`isp.gainMin` / `isp.shutterMinUs`** (v0.46.0) — the floors that close the manual envelope alongside the existing ceilings. `0` = use the ISP bin's calibrated limit. Each floor is clamped so it can never exceed its ceiling
- **`isp.shutterMaxUs`** (v0.44.0) — set above the frame period, it makes the sensor skip frames: a soft way to lower effective fps **without the ~0.5 s** bind-rebind stall
- **`isp.shutterRule180`** (v0.41.0) — the 180° shutter rule: exposure pinned to exactly 1/(2×fps). At 60 fps that is 8333 µs; the shutter is locked while gain still auto-adjusts for brightness
- **a new userspace AWB on Star6E** (v0.56.0): white balance was frozen — two things in the pipeline left AWB with nothing driving it. It is now a dedicated loop that does not pay for it in frame rate

### 🔹 Sensor drivers: a clean reset edge

Fixed a defect that could leave the **sensor not answering on i2c at all** (`MI_SNR_Enable` = `0xA01B201F`, every mode's init table NAK'ing).

`pCus_poweron()` never produced a clean reset edge: on Maruko it did not touch PWDN/RESET at all (the toggle lived in `pCus_HardwareReset()`, which nothing called), and on Star6E the first pair used the release polarity. Both IMX335 drivers now run the canonical SDK sequence — **v0.60.1** (Maruko, contributed by @tipoman9, verified on SSC378QE + IMX335) and **v0.60.2** (Star6E).

The same release fixed `isp.keepAspect=false` on Maruko: since v0.24.1 it had been hardcoded to `true`, silently centre-cropping every AR-mismatched pipeline and reducing a documented contract to a printed note.
