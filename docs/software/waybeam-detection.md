# Детекція об'єктів на NPU

Waybeam уміє запускати детектор об'єктів на **простоюючому IPU/NPU** камери й розсилати результат як покадрові метадані — рамки летять поруч із відео, у тій самій телеметрії, і переживають втрати в радіоканалі.

::: info Де це працює
Star6E (Infinity6E) та Maruko (Infinity6C). На **CV610 детекції немає**. Довідник звірено з версією **v0.73.3**.
:::

---

### Плагінна архітектура — і чому вона така

Ключове рішення: **сама модель у waybeam не входить**.

| Хто чим володіє | |
| :--- | :--- |
| **Хост (waybeam)** | тап кадрів під розмір входу моделі (NV12, drop-not-block), потік читання, конфіг, транспорт результату |
| **Плагін (`.so`)** | пристрій IPU, завантаження `.img`-моделі, декод виходу, таблиця класів |

Плагін віддає хосту простий масив `DetectBox[]` — і на цьому межа. Наслідок: **нова модель це зміна конфіга, а не перезбирання waybeam**. Усе модельно-специфічне живе поза репозиторієм waybeam, тож ви можете возити власні моделі, не форкаючи енкодер.

Хост тримає подвійно буферизований знімок (до 64 рамок), який читають одразу два споживачі — sidecar і OSD. М'ютекс утримується лише на час копіювання і **ніколи** — на час виклику IPU.

::: tip Детекція — best-effort, вона не може завалити політ
Будь-яка помилка при піднятті детектора логується, і потік просто йде далі без нього. Це свідоме проєктне рішення: відео важливіше за рамки.
:::

### Куди йде результат

<strong>1. DETECT-трейлер у RTP-sidecar</strong>

Флаг `0x10`, додається **останнім** серед трейлерів:

| Частина | Вміст |
| :--- | :--- |
| Заголовок (16 Б) | `model_id`, `schema_ver`, кількість рамок, `detect_seq`, довжина payload, вік у мс |
| Тіло | TLV із BOX-записами у нормалізованих `u16` |

Трейлер чіпляється до **кожного** кадру, поки є хоч один підписник — саме щоб рамки пережили втрати в ефірі. Заради цього шлях відправки sidecar перебудували навколо 512-байтового датаграмного буфера зі змінними трейлерами, впорядкованими за прапорцями.

Сам sidecar **мультипідписний** (до 4 одержувачів, TTL 5 с на слот), тож HUD із рамками і adaptive-link контролер слухають телеметрію паралельно, не «викрадаючи» її один в одного.

<strong>2. Рамки на debug-OSD</strong>

`detect.osd` (потребує `debug.showOsd`): прохід OSD у потоці кодування масштабує опублікований знімок на канву і малює прямокутники з палітрою за класами плюс рядок `det N`.

Знімки старші за **700 мс не малюються** — краще порожній кадр, ніж рамка, що відстала від картинки.

### Поля конфігурації

Секція `detect` у `/etc/waybeam.json`:

| Поле | Мутабельність | Опис |
| :--- | :--- | :--- |
| `enabled` | **live** | Увімкнути детектор (з v0.53 — без рестарту) |
| `plugin` | restart | Шлях до `.so`-плагіна |
| `modelPath` | **live** | Шлях до `.img`-моделі — гаряча заміна |
| `firmwarePath` | restart | Прошивка NPU |
| `inferInterval` | live | Виконувати інференс раз на N кадрів |
| `osd` | live | Малювати рамки на debug-OSD |
| `confThresh` | **live** | Поріг впевненості. `<=0` — дефолт плагіна |
| `nmsIou` | **live** | Поріг NMS IoU. `<=0` — дефолт плагіна |
| `netWidth` / `netHeight` | restart | Геометрія тапу під модель |
| `modelId` | live | Селектор таблиці класів для sidecar |

```json
"detect": {
  "enabled": false,
  "plugin": "",
  "modelPath": "",
  "firmwarePath": "",
  "inferInterval": 1,
  "osd": false,
  "confThresh": 0.20,
  "nmsIou": 0.0,
  "netWidth": 640,
  "netHeight": 352,
  "modelId": 0
}
```

::: warning Усі поля `detect` — append-only в кінці структури
Конфіг-ABI навмисно розширюється тільки в хвіст: завантаження ISP-bin на SigmaStar ламається, якщо layout `VencConfig` зсувається. Це не стиль, це вимога.
:::

### Керування на льоту

```bash
# Увімкнути / вимкнути детектор без рестарту
curl "http://<ip>/api/v1/set?detect.enabled=true"

# Гаряча заміна моделі — пайплайн не респавниться, потік не рветься
curl "http://<ip>/api/v1/set?detect.modelPath=/opt/models/sar_person.img"

# Пороги
curl "http://<ip>/api/v1/set?detect.confThresh=0.20&detect.nmsIou=0.45"
```

Заміна виконується на потоці пайплайна (encode thread), тож вона **атомарна щодо кадру**. Модель, чия заявлена геометрія входу не збігається з налаштованим тапом, **відхиляється** — і детекція лишається вимкненою, а не працює на сміттєвих даних.

::: tip Поріг варто ставити ~0.20, а не 0.40
Це не «менш строго», це виправлення систематичного зсуву. INT8-квантизація з'їдає близько **30% скору** порівняно з FP32 саме на дрібних об'єктах — а дрібні об'єкти і є цільове навантаження. Задум архітектури: детектор працює на ~`0.20`, а шум відсіює трекер на землі за правилом «2 влучання».

До **v0.51.0** ці поля взагалі не доходили до плагіна — хост слав нулі, і кожен бекенд мовчки працював на своїх вбудованих `0.40` / `0.45`.
:::

### Геометрія тапу

`detect.netWidth` / `netHeight` замінили зашиті `640×352` — геометрію, успадковану від чужої моделі VisDrone, а не обрану під ваш сенсор. Це була **найбільша окрема перешкода** для розпізнавання дрібних об'єктів.

Обмеження:

- обидва значення мають бути **кратні 32** (голова моделі має страйди 8/16/32)
- обидва мають **збігатися** зі скомпільованим `.img` — бекенд і так відхиляє невідповідний кадр
- поля **restart**: геометрія фіксується при створенні порту
- `0` означає `640` / `352`

---

### `modelId` — чому його не можна вивести автоматично

`detect.modelId` кладе селектор таблиці класів у DETECT-трейлер. До v0.51.0 він був **зашитий у VisDrone**, тож одноклясова SAR-модель (пошук людини) представлялась як VisDrone-10, і кожна рамка приїжджала на землю з підписом **«pedestrian»**.

Вивести його неможливо: плагін вантажить той `.img`, який названо в `modelPath`, і більше про нього нічого не відомо. Тому це **операторський конфіг**.

Хост при старті викликає в плагіна хук `describe()` і **попереджає**, якщо заявлена кількість класів суперечить налаштованому `modelId`. Невідомі id перевірку пропускають — приватний `model_id` цілком легітимний.

---

### Обмеження

::: danger Детекція і стабілізація взаємовиключні
Обидві претендують на один і той самий тап: **VPE port1** на Star6E, **SCL port3** на Maruko. Увімкнути `detect` разом із `video0.framing=stab` не вийде.

Порядок претендентів на port1: спершу стабілізація, потім детектор, і **останнім** — QR-сканування.
:::

- на **CV610** детекції немає взагалі
- `netWidth`/`netHeight` потребують рестарту (див. вище)

### Історія: чому це не одразу було живим

::: details v0.48–v0.53 — детекція була Star6E-only і потребувала рестарту
У першій версії (**v0.48.0**) поле `detect.enabled` було restart-класовим, а на Maruko `/api/v1/set?detect.enabled=...` повертав `501`.

Спроба зробити його живим впиралася у справжню ваду: після `set?detect.enabled=false` свіжий процес **заклинювало**. Причина виявилась не в часі й не в стані порту, як здавалося спочатку, а в **успадкованому дескрипторі `/dev/mi_sys`**.

У **v0.53.0** поле стало `MUT_LIVE` через окремий шлях старт/стоп детектора, а `iy_unload_graph()` навчився звільняти користувацький вихід порту. У **v0.54.0** додали «скраб» стану: хоч би що лишав по собі попередник, наступник це вичищає.

Паритет із Maruko (детектор на SCL port 3, разом із живим вмиканням, заміною моделі та `detect.osd`) прийшов у контракті API **0.15.0**.
:::

::: details v0.52.0 — як зробили гарячу заміну моделі
До цього зміна моделі означала перезапуск пайплайна: чорний кадр у пілота посеред польоту.

У v0.52.0 з'явився окремий вхід перезавантаження **лише детектора**, а ABI плагіна піднявся до `2` — тепер геометрія моделі перевіряється проти тапу. Живий шлях береться тільки коли `netWidth`/`netHeight` збігаються.

Заміряно: зміна моделі **не респавнить пайплайн, не роняє кадри й не рве потік**. Граф перезавантажується лише коли справді змінилася модель — `model_id` це просто мітка у трейлері, її зміна графа не чіпає.
:::

::: details v0.51.1 — загартовування проти поганих плагінів
Чотири захисні виправлення, що нічого не міняють на нормальному шляху, але закривають те, що може прийти з плагіна поза контрактом:

- **ідемпотентне завантаження `libmi_sys`** — детектор відкривав бібліотеку на кожному старті й ніколи не закривав, тож кожен SIGHUP-reinit нарощував лічильник dlopen без межі
- **затиск float→піксель перед приведенням типу** — шлях OSD затискав лише знизу, тож величезне / `inf` / `NaN` значення від плагіна поза контрактом потрапляло в невизначену поведінку
- **NaN-безпечна квантизація на дроті** — перевірки `<=0` / `>=1` пропускають `NaN` (усі порівняння хибні); переписано як `!(x > 0)`, щоб `NaN` давав 0
- **захист від переповнення в `ipu_probe`** — кількість елементів тензора перевіряється на переповнення множення перед `malloc`
:::
