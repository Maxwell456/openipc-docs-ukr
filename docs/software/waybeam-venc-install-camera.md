# Встановлення Waybeam на камеру

Ця інструкція описує, як встановити **Waybeam** на камеру з чіпом SigmaStar (Infinity6E / Infinity6C) або HiSilicon (Hi3516CV610) та налаштувати його для роботи з **WFB-ng** замість Majestic.

::: info Що таке Waybeam?
**Waybeam** — це автономний H.265 (HEVC) відеоенкодер, який повністю замінює Majestic. Він забезпечує нижчу затримку, повний HTTP API для налаштування в реальному часі, та нативну інтеграцію з WFB-ng через Unix-сокет. Бінарник, конфіг (`/etc/waybeam.json`) та init-скрипт мають назву `waybeam`.

Інструкцію звірено з версією **v0.73.3** (кінець серпня 2026).
:::

::: warning Оновлюєтесь із версії до v0.73? Прочитайте це першим
- **`video0.maxIBytes` / `video0.maxPBytes` видалено** у v0.72.0 — вимірювання показали, що вони ніколи не тримали ту межу, яку обіцяли. Конфіг із цими ключами завантажиться (невідомі ключі ігноруються), але `/api/v1/set` чи `/api/v1/live/set` із ними **відхилить увесь запит** з `404 unknown config field`. Приберіть їх зі збережених профілів.
- **`outgoing.shmThrottle` видалено** у v0.69.0 — те саме правило: конфіг терпить, API — ні.
- **`isp.aeEngine: "custom"` видалено** у v0.47.0 — приймається лише `"sdk"`.
- **Дефолт `video0.qpDelta` змінено з `0` на `-12`** (Star6E, Maruko), щоб обмежити вартість IDR.
:::

### Крок 1: Підключення до камери через SSH

Підключіться до камери по SSH. IP-адреса камери зазвичай `192.168.1.10` або визначається через роутер.

::: code-group

```powershell [Windows (PowerShell)]
ssh root@192.168.1.10
# пароль: 12345
```

```bash [macOS / Linux]
ssh root@192.168.1.10
# пароль: 12345
```

:::

::: tip Графічний клієнт для Windows
Замість командного рядка можна скористатися [PuTTY](https://www.putty.org/): у полі «Host Name» — IP камери, порт `22`, тип `SSH`, логін `root`, пароль `12345`.
:::

---

### Крок 2: Зупинка Majestic

Перед встановленням Waybeam необхідно зупинити та вимкнути Majestic:

```bash
# Зупинити Majestic
killall majestic 2>/dev/null

# Вимкнути автозапуск Majestic
# (якщо він запускається через init-скрипт)
if [ -f /etc/init.d/S95majestic ]; then
    chmod -x /etc/init.d/S95majestic
fi
```

::: warning Важливо
Majestic і Waybeam не можуть працювати одночасно — вони обидва використовують ISP та відеоенкодер чіпа.
:::

---

### Крок 3: Завантаження Waybeam

Релізи поставляються тарболами, які містять бінарник `waybeam`, шаблон конфігурації `waybeam.json` і (для Maruko) потрібні бібліотеки SigmaStar. Оберіть тарбол відповідно до вашого чіпа.

::: code-group

```bash [Star6E · SSC30KQ / SSC338Q]
cd /tmp
curl -L -o waybeam-star6e.tar.gz \
  https://github.com/OpenIPC/waybeam/releases/latest/download/waybeam-star6e.tar.gz
tar xzf waybeam-star6e.tar.gz

# Встановити бінарник
cp waybeam /usr/bin/waybeam
chmod +x /usr/bin/waybeam
```

```bash [Maruko · SSC378QE]
cd /tmp
curl -L -o waybeam-maruko.tar.gz \
  https://github.com/OpenIPC/waybeam/releases/latest/download/waybeam-maruko.tar.gz
tar xzf waybeam-maruko.tar.gz

cp waybeam /usr/bin/waybeam
chmod +x /usr/bin/waybeam
```

```bash [CV610 · Hi3516CV610]
cd /tmp
curl -L -o waybeam-cv610.tar.gz \
  https://github.com/OpenIPC/waybeam/releases/latest/download/waybeam-cv610.tar.gz
tar xzf waybeam-cv610.tar.gz

cp waybeam /usr/bin/waybeam
chmod +x /usr/bin/waybeam
```

:::

::: warning Maruko потребує бібліотек
Стокова прошивка OpenIPC для Infinity6C **не містить** vendor-бібліотек SigmaStar (MI). Бібліотеки з тарболу потрібно скопіювати в `/usr/lib/`, а також можуть знадобитися сенсорні `.ko`-модулі та ISP `.bin`-файли. Деталі та скрипти провізіонінгу — у [README репозиторію](https://github.com/OpenIPC/waybeam#maruko-infinity6c).
:::

::: warning CV610 ставиться інакше <Badge type="tip" text="v0.65+" />
Бекенд **CV610** (HiSilicon Hi3516CV610 + Sony IMX662) з'явився у v0.65.0 і має власний порядок встановлення. У тарболі, крім бінарника, лежать:

- `sensors/` — сенсорний плагін IMX662 (збирається з джерел, не пропрієтарний бінарник)
- `S95waybeam` — init-скрипт, перевірений на залізі: він вантажить MPP-модулі та **відмовляється їх вивантажувати, поки граф має власника**
- `waybeam-cv610.conf` — профіль тактової частоти сенсора для платформного завантажувача
- `waybeam.json` — дефолтний конфіг CV610 (`1280x720@100`, 2600 kbps, вихід одразу у `frame-shm://venc_wfb`)

Аудіо на CV610 вмикається **тільки через JSON + платформний конфіг**, а не через HTTP: демон не може безпечно довантажити opt-in kernel-модулі під час респавну.

Не використовуйте `S95waybeam reload` — цю дію **видалено у v0.65.10** разом із відкатом модулів при невдалому старті: обидва шляхи вивантажували MPP-модулі під живим споживачем і могли підвісити SoC. Правильне відновлення після падіння — звичайний `restart`.
:::

::: tip Альтернативний метод — SCP зі зібраного бінарника
Якщо ви збираєте Waybeam самостійно (`make build SOC_BUILD=star6e`):
```bash
scp out/star6e/waybeam root@192.168.1.10:/usr/bin/waybeam
```
:::

Поля `video0.codec` більше немає — Waybeam кодує тільки H.265 (HEVC). Старі конфіги з `"codec": "h264"` чи `"h265"` завантажуються без помилок, але ключ ігнорується.
:::

У старих версіях секція `video0` містила SDK-стратегію пропуску кадрів при перевантаженні:

```json
"video0": {
  "...": "...",
  "frameLost": true
}
```

У **v0.19** цю стратегію прибрано повністю — поля `frameLost` більше не існує ані в конфізі, ані в API; натомість діє нижня межа бітрейту **1000 kbps**. Якщо ключ лишився у вашому старому конфізі — видаліть цей рядок.
:::

### Крок 5: Ключові параметри конфігурації

<strong>Відео (`video0`)</strong>

| Параметр | Опис | Типові значення |
| :--- | :--- | :--- |
| `rcMode` | Режим керування бітрейтом | `"cbr"`, `"vbr"`, `"avbr"`, `"fixqp"` |
| `fps` | Частота кадрів (макс. залежить від режиму сенсора) | `30`, `60`, `90`, `100`, до `144` |
| `size` | Роздільна здатність | `"auto"`, `"1920x1080"`, `"1280x720"` |
| `bitrate` | Бітрейт (кбіт/с), мінімум `1000` | `4096` — `16384` |
| `gopSize` | Розмір GOP у секундах (діє лише коли `resilience: "off"`) | `0.5` — `4.0` |
| `qpDelta` | Зсув QP I-кадрів відносно P. **Дефолт `-12`** (Star6E, Maruko); на CV610 поля немає | `-12` — `12` |
| `minQp` / `maxQp` | **live** межі QP для rate-control. `0` = дефолт драйвера | `0`, або `20`—`45` |
| `sliceCount` | Кількість слайсів H.265 на кадр (restart). `1` = як раніше | `1` — `32` |
| `resilience` | Пресет стійкості до втрат (потребує **reboot**) | `"off"`, `"racing"`, `"ltr"`, `"fpv"`, … |
| `intraRefreshQp` | QP смуги intra-refresh — **тільки CV610** | `0` (авто) — `51` |
| `framing` | Стабілізація / цифровий зум (SigmaStar) | `"off"`, `"stab"`, `"zoom-2x"`, … |

::: tip Нове у v0.41–v0.73 <Badge type="tip" text="актуально" />
- **`video0.minQp` / `maxQp`** — живі межі QP. З'явилися на Star6E у v0.64, на CV610 — у v0.65.6, на **Maruko — у v0.73.0**. На Star6E запит `minQp > maxQp` тепер відхиляється, а не записується мовчки.
- **`video0.sliceCount`** — багатослайсове H.265: кадр ділиться на N незалежних слайсів, тож втрата пакета понад бюджет FEC псує **ділянку** кадру, а не весь кадр. Star6E — з v0.66.0, CV610 і Maruko — з v0.67.0. Діапазон запиту 1..32, реально доставлену кількість обмежує геометрія (на Maruko 720p — максимум 12).
- **`video0.resilience = "ltr"` / `"ltr:<N>"`** (v0.64.0) — половина кадрів нереференсні при збереженому вашому `gopSize`, тож половина втрат коштує рівно один кадр. Чим менше `N`, тим стійкіше (`ltr` = `ltr:1`). Ціна по бітрейту — менше 1%. Пресет **не OSD-safe**.
- Невідоме значення `resilience` тепер повертає **409**, а не приймається мовчки з попереднім пресетом у похідних полях.
:::

::: info Детальніше про framing, resilience та attitude
Режими стабілізації/зуму (`framing`), пресети стійкості (`resilience`) та штучний горизонт з IMU (секція `attitude`, v0.39+) докладно описані у розділі [Веб-панель та HTTP API](/software/waybeam-venc-web-interface).
:::

::: details Для версій v0.45–v0.71 — поля `video0.maxIBytes` / `maxPBytes`
У **v0.45.0** з'явилися live-межі розміру окремого I- та P-кадру (`u32MaxISize` / `u32MaxPSize` у RC-параметрах MI_VENC), а у v0.49.0 їх винесли в дешборд. У **v0.72.0 їх видалено повністю** — вимірювання на SSC338Q (720p60, H.265 CBR, GDR) показало, що вони не тримають заявленої межі: при `maxPBytes` від 33144 до 6000 байт реальний бітрейт зсунувся менш ніж на 0.3%, а перепис access unit'ів знайшов **усі 863 кадри понад межею** (у середньому 40247 B).

Конфіг зі старими ключами завантажується (невідомі ключі ігноруються, і ключі зникають при наступному записі конфіга), але `GET /api/v1/set` **або** `GET /api/v1/live/set` з їхньою згадкою відхиляє **весь запит** із `404 unknown config field`. Приберіть їх зі збережених «профілів» на наземній станції.

**Чим замінити:** для розміру I-кадру — `video0.qpDelta` (діапазон впливу в 68× на тому ж стенді, і він не форсує кейфрейм). Для P-кадру прямої заміни немає; лишається `video0.minQp`.
:::

::: details Для версій до v0.47 — `isp.aeEngine: "custom"`
Поле `isp.aeEngine` на Star6E приймало `"sdk"` і `"custom"`. У **v0.47.0** значення `"custom"` **видалено**: з'ясувалося, що потік `cus3a` ніколи не робив зведення AE — його завжди вів ISP-firmware/bin. Тепер приймається лише `"sdk"`; старий конфіг зі `"custom"` завантажується з попередженням і мовчазним відкатом на `sdk`. Наглядовий потік лишився як «сторож меж» `isp.gainMin/Max` + `isp.shutterMinUs/MaxUs`.
:::

<strong>Стрімінг (`outgoing`)</strong>

| Параметр | Опис | Приклади |
| :--- | :--- | :--- |
| `enabled` | Увімкнути стрімінг | `true` / `false` |
| `server` | Адреса приймача | `"unix://wfb_tx"`, `"udp://192.168.1.1:5600"`, `"shm://venc_ring"`, `"frame-shm://venc_wfb"` |
| `streamMode` | Режим потоку | `"rtp"` або `"compact"` |
| `maxPayloadSize` | Макс. розмір RTP-пакету | `1400` (за замовч.) |
| `connectedUdp` | Підключений UDP-сокет (`connect()`) | `true` (за замовч.); `false` — unconnected, використовується у WiFi-режимі apfpv |
| `audioPort` | Аудіоканал | `0` — разом з відео; `>0` — окремий UDP-порт; `<0` — аудіо лише в запис, не в ефір |

::: tip Транспорт `frame-shm://` <Badge type="tip" text="v0.42+" />
Новий транспорт передає **цілі закодовані кадри** через POSIX shared memory, повністю оминаючи RTP-пакетизацію: споживач (waybeam-link) сам робить framing і FEC на межах кадрів. Кільце — SPSC lock-free, 8 слотів × 384 KiB, і кожен кадр несе метадані: прапорці **GDR** / **ENHANCE** / **SALVAGED**, а також позицію в циклі intra-refresh (`gdr_pos` / `gdr_len`) — щоб транспорт міг посилювати FEC саме там, де цикл добігає кінця.

Це **дефолтний вихід на CV610**. `apply_server` (живе перенацілення) для SHM-виходів не працює — зміна `outgoing.server` на frame-shm потребує рестарту.

⚠️ У **v0.69.0** заголовок кільця став **версії 2** (зміщення 88 змінило сенс: було `throttle_permille`, стало `low_water_slots` — і полярність інвертована, менше = здоровіше). Producer v2 **не обслуговує consumer v1**: waybeam-link, waybeam-hub і radeon-vrx треба перезбирати разом із камерою.
:::

::: details Для версій v0.57–v0.68 — поле `outgoing.shmThrottle`
У **v0.57.0** з'явився AIMD-регулятор, що притискав бітрейт енкодера за заповненням SHM-кільця, і поле `outgoing.shmThrottle` (за замовчуванням увімкнене). У **v0.69.0 його видалено разом із самим механізмом**: на `frame-shm://`-крафті регулятор швидкості (waybeam-link) і так живе поруч, і так читає те саме кільце, і так володіє `video0.bitrate` — виходило два контролери на одному сигналі, причому єдиний актуатор другого форсував кейфрейм.

Заміряно 24 серпня на Star6E 720p120: з клампом — 6.5 IDR/с і 100–143 мс glass-to-glass; без клампа — 0.2 IDR/с і 15–37 мс.

Тоді ж прибрано і **recovery-IDR при повному кільці**: запит спрацьовував саме тоді, коли найбільший кадр потоку однаково не міг бути доставлений (13 IDR за 12 с, жоден не дійшов). З `/api/v1/transport/status` зникли `throttlePermille` і `effectiveBitrateKbps`, натомість з'явилися `ringLowWaterSlots`, `otherDrops` і `badAuDrops`.

Конфіг зі старим ключем завантажується, але `POST /api/v1/set` із ним відхиляє **весь батч**.
:::

<strong>Виявлення в мережі (`discovery`)</strong>

Камера анонсує себе через mDNS — її можна відкривати як `http://waybeam.local`, без пошуку IP:

| Параметр | Опис | За замовч. |
| :--- | :--- | :--- |
| `enabled` | mDNS-анонс у локальній мережі | `true` |
| `serviceType` | Тип сервісу | `"_waybeam-venc._tcp"` |
| `name` | Власне ім'я; порожнє — `waybeam-<суфікс>`, де суфікс — хвіст die ID чипа | `""` |
| `bareAlias` | Додатково коротке ім'я `waybeam.local` (конфлікт кількох камер вирішується за RFC 6762) | `true` |

Повний 12-значний серійник (die ID) читається з `GET /api/v1/config` → `data.device.serial`.

<strong>Експозиція та підсилення (`isp`)</strong>

Наглядовий потік тримає ці межі поверх штатної firmware-AE. Усі чотири — **live**, `0` означає «взяти калібровану межу з ISP-bin».

| Параметр | Опис | З версії |
| :--- | :--- | :--- |
| `gainMax` | Стеля сенсорного підсилення | давно |
| `shutterMaxUs` | Стеля витримки (мкс). Значення понад період кадру змушує сенсор пропускати кадри — м'яке зниження ефективного fps без ~0.5 с стопору на rebind | v0.44.0 |
| `gainMin` | **Підлога** підсилення | v0.46.0 |
| `shutterMinUs` | **Підлога** витримки (мкс) | v0.46.0 |
| `shutterRule180` | Правило 180° затвора: витримка жорстко дорівнює 1/(2×fps) — на 60 fps це 8333 мкс. Затвор зафіксовано, підсилення далі підлаштовується під яскравість. **restart** | v0.41.0 |

Кожна підлога автоматично затискається так, щоб ніколи не перевищити свою стелю, а `shutterRule180` (він пінить `min == max`) має пріоритет над ручним `shutterMinUs`.

<strong>Детекція об'єктів (`detect`)</strong> <Badge type="tip" text="v0.48+ · Star6E, Maruko" />

Детектор працює на простоюючому IPU/NPU і **не входить у постачання waybeam** — сама модель, декодер і таблиця класів живуть у плагіні `.so`, який ви кладете на камеру окремо. Зміна моделі = зміна конфіга, без перезбирання waybeam.

| Параметр | Опис |
| :--- | :--- |
| `enabled` | Увімкнути детектор (**live** з v0.53) |
| `plugin` | Шлях до `.so`-плагіна |
| `modelPath` | Шлях до `.img`-моделі (**live** — гаряча заміна без розриву потоку, v0.52) |
| `firmwarePath` | Прошивка NPU |
| `inferInterval` | Виконувати інференс раз на N кадрів |
| `osd` | Малювати рамки на debug-OSD (потребує `debug.showOsd`) |
| `confThresh` | Поріг впевненості. `<=0` — дефолт плагіна. Рекомендовано ~`0.20`: INT8-квантизація з'їдає ~30% скору на дрібних об'єктах, а трекер на землі відсіює шум за правилом «2 влучання» |
| `nmsIou` | Поріг NMS IoU. `<=0` — дефолт плагіна |
| `netWidth` / `netHeight` | Геометрія тапу під модель — обидва кратні 32 і мають збігатися з `.img` (**restart**) |
| `modelId` | Селектор таблиці класів для DETECT-трейлера sidecar. Без нього одноклясова SAR-модель представлялась як VisDrone-10 і кожна рамка підписувалась «pedestrian» |

::: warning `detect` і `framing=stab` взаємовиключні
Обидва претендують на один і той самий тап (VPE port1 на Star6E, SCL port3 на Maruko). Увімкнути обидва одночасно не вийде. На CV610 детекції немає взагалі.
:::

<strong>QR-сканування (`qr`)</strong> <Badge type="tip" text="v0.60+ · Star6E" />

| Параметр | Опис |
| :--- | :--- |
| `tapEnabled` | Увімкнути luma-тап **без накладеного OSD** (щоб оверлей не псував маркер) |
| `tapWidth` / `tapHeight` | Роздільність тапу; `0` — за роздільністю snapshot |
| `windowMs` | Тривалість вікна сканування за замовчуванням (**live**: наступний скан бере нове значення) |

::: danger Waybeam декодує маркер, але нічого з ним не робить
Парування, команди й диспетчеризація дій **не реалізовані** і свідомо винесені за межі бінарника waybeam. Камера повертає вам 16 символів через `/api/v1/qr/status` — і зупиняється: вона **не інтерпретує, не авторизує, не зберігає й не виконує** цей payload. Що ці символи означають, вирішує ваш власний шар поверх API.
:::

<strong>Формат маркера</strong>

Приймається лише жорстко зафіксований конверт — це навмисно, щоб не робити глобальних сканів по кадру:

```text
PXXXXXXXXXXXXXXX
```

- QR **Version 1** (21 × 21 модулів), корекція помилок **Q**, алфавітно-цифровий режим
- рівно **16** символів з алфавіту `0-9 A-Z` та `` $%*+-./:``
- перший символ — тип: **`P`** (зарезервовано під парування/парольну фразу) або **`C`** (під команди/налаштування)
- решта 15 символів для декодера **непрозорі**

Обов'язкова також **зовнішня рамка** — без неї стандартний, але необрамлений QR ігнорується:

```text
33 × 33 модульних одиниці разом
2 модулі суцільної чорної зовнішньої рамки
4 модулі білої тихої зони всередині рамки
QR 21 × 21 у координаті (6, 6)
```

Суцільний контур дає чотири стабільні проєктивні кути, з яких декодер одразу відображає сітку QR — тому глобальний пошук finder-патернів у продакшн-декодері **не запускається ніколи**.

<strong>Згенерувати маркер</strong>

```bash
python3 -m pip install -r tools/qr/requirements-generator.txt
python3 tools/qr/generate_qr.py P23456789ABCDEFG waybeam-pair.svg
python3 tools/qr/generate_qr.py CRES1080P60A0030 command.png --scale 30
```

`--scale` — ціла кількість пікселів на модульну одиницю для растру.

::: tip Скільки пікселів треба на модуль
Лабораторний мінімум — близько **3 px/модуль**, реалістична ціль для камери — **4 px/модуль**. Бюджет витрачається на роздільність MJPEG-каналу (`snapshot.width` / `snapshot.height`), тож для розпізнавання **з більшої відстані збільшуйте канал**. JPEG q80 по люмі декодується надійно.

Заміряно на стенді (768 згенерованих зображень 1280×720, чотири ширини маркера, стиснення до 0.35, три повороти, чотири напрямки перспективи, чотири рівні розфокусу): рамку ідентифіковано у **100%** випадків, payload декодовано у **92.3%** — проти **65.9%** у стокового quirc без рамки. Ті самі числа відтворено нативно на стенді SSC338Q.
:::

<strong>Перевірити вручну</strong>

```bash
# Прямо з камери, без відкриття вікна сканування
curl -s http://127.0.0.1/api/v1/snapshot.jpg | qr_decode

# Діагностика: які проходи спрацювали і скільки часу зайняли
qr_decode --stats capture.jpg

# Поллінг без жодних дій — просто друкує валідні конверти
qr_watch.sh -c -v
```

Для цього потрібен `snapshot.enabled: true`. `qr_watch.sh` повертає HTTP `503`, якщо знімки вимкнено.

<strong>FPV ROI-кодування (`fpv`)</strong>

| Параметр | Опис | Значення |
| :--- | :--- | :--- |
| `roiEnabled` | Пріоритет центру кадру | `true` — центр у вищій якості |
| `roiQp` | QP-зсув для ROI (`-30`…`30`) | `-18` — максимальна якість центру |
| `roiSteps` | Кількість зон | `1` — `4` |
| `roiCenter` | Розмір центральної зони | `0.1` — `0.9` |

### Крок 7: Автозапуск Waybeam

Створіть init-скрипт для автоматичного запуску Waybeam при завантаженні камери:

```bash
cat > /etc/init.d/S96waybeam << 'INITEOF'
#!/bin/sh

case "$1" in
  start)
    echo "Starting waybeam..."
    # Переконатися, що Majestic не запущений
    killall majestic 2>/dev/null
    # Запуск waybeam у фоновому режимі
    start-stop-daemon -S -b -x /usr/bin/waybeam -- 2>&1 | tee /tmp/waybeam.log &
    ;;
  stop)
    echo "Stopping waybeam..."
    killall waybeam 2>/dev/null
    ;;
  restart)
    $0 stop
    sleep 1
    $0 start
    ;;
  *)
    echo "Usage: $0 {start|stop|restart}"
    exit 1
    ;;
esac

exit 0
INITEOF

chmod +x /etc/init.d/S96waybeam
```

::: tip Порядок запуску
Скрипт має номер `S96`, що означає запуск після більшості системних сервісів, але вам потрібно переконатися, що WiFi-драйвери та WFB-ng вже завантажені до цього моменту (особливо для `unix://wfb_tx`, де `wfb_tx` має слухати сокет раніше).
:::

::: info audioPort та sidecarPort
У конфізі вище `audioPort: 0` і `sidecarPort: 0`. Це означає:

- `audioPort: 0` — аудіо передається разом з відео через той самий канал (оптимально для WFB-ng)
- `audioPort < 0` (наприклад, `-1`) — режим «лише запис»: звук пише у файл на SD, але в ефір не відправляється
- `sidecarPort: 0` — sidecar-канал діагностики вимкнений (ніяких накладних витрат)

Дефолтний шаблон має `audioPort: 5601` і `sidecarPort: 5602` — якщо вам потрібна окрема передача аудіо чи покадрова телеметрія через UDP, встановіть відповідні значення.
:::

### Крок 8: Зміна параметрів у реальному часі

Після запуску Waybeam ви можете змінювати параметри без перезапуску:

```bash
# Змінити бітрейт (live)
curl "http://localhost/api/v1/set?video0.bitrate=4096"

# Змінити роздільну здатність (потребує reinit)
curl "http://localhost/api/v1/set?video0.size=1280x720"

# Змінити FPS (live)
curl "http://localhost/api/v1/set?video0.fps=90"

# Увімкнути ROI для FPV (live)
curl "http://localhost/api/v1/set?fpv.roiEnabled=true"
curl "http://localhost/api/v1/set?fpv.roiQp=-18"

# Запит IDR-кейфрейму (корисно після підключення)
curl http://localhost/request/idr
```

::: tip `/api/v1/live/set` — зміна без запису на флеш <Badge type="tip" text="v0.50+" />
Звичайний `/api/v1/set` **зберігає** значення у `/etc/waybeam.json`. Для високочастотних автоматичних записів (адаптивний бітрейт waybeam-link) це погано двічі: зношується флеш, і камера завантажиться в останній адаптивний «перехідний» стан.

`/api/v1/live/set` має точно ту саму поверхню полів і байт-у-байт ті самі відповіді, але пише **лише в оперативний конфіг**:

```bash
curl "http://localhost/api/v1/live/set?video0.bitrate=4096"
```

Тільки live-поля. Restart-поле поверне `400` («restart-class field requires persistence; use /api/v1/set») — бо reinit пайплайну перечитує конфіг із диска й мовчки викинув би ваше значення. Наступний персистуючий `/set` чи `/defaults` збереже увесь поточний стан разом із волатильними змінами. Старі збірки без цього ендпоінта повертають 404 — клієнти пробують один раз і відкочуються на `/set`.
:::

### Поширені проблеми

::: details Waybeam не запускається — помилка бібліотек
Переконайтеся, що всі бібліотеки SigmaStar доступні в `/usr/lib`. На Maruko їх потрібно встановити з тарболу вручну. Якщо ви використовуєте staged-збірку, встановіть змінну:

```bash
export LD_LIBRARY_PATH=/шлях/до/lib
```
:::

::: details Немає відео після запуску
1. Перевірте, що `outgoing.enabled` встановлено в `true`
2. Перевірте правильність адреси `outgoing.server`
3. Перевірте, що Majestic повністю зупинений: `ps | grep majestic`
4. Перевірте логи: `cat /tmp/waybeam.log`
:::

::: details Чорний екран або артефакти
Перевірте сумісність сенсора:

```bash
# Поточний сенсор і доступні режими
curl http://localhost/api/v1/modes
```

Переконайтеся, що `sensor.index` та `sensor.mode` встановлені на `-1` (автовизначення).

**Оновилися зі старої версії?** Лінійки режимів сенсорів перебудовано кілька разів: v0.21/v0.23 (Maruko), **v0.25–v0.34** (Star6E, власні in-tree драйвери IMX335/IMX415). **Індекси `sensor.mode` перенумеровано**, а частину режимів приховано — збережений у конфізі індекс поза новим діапазоном не дає waybeam стартувати (помилка вибору режиму при завантаженні). Звірте старий конфіг зі списком `/api/v1/modes` або поверніть `-1`.
:::

::: details Сенсор взагалі не відповідає по i2c (`MI_SNR_Enable` = `0xA01B201F`)
Це не ваш конфіг — це була вада драйвера IMX335, виправлена у **v0.60.1 (Maruko)** та **v0.60.2 (Star6E)**.

Функція `pCus_poweron()` не давала чистого фронту скидання: на Maruko вона взагалі не чіпала PWDN/RESET (перемикання жило у `pCus_HardwareReset()`, який ніхто не викликав), а на Star6E перша пара PWDN/RESET використовувала полярність «відпустити», тож послідовність виходила «відпустити → налаштувати CSI → відпустити знову». На платах, які тримають сенсор у скиданні, доки драйвер його не відпустить, **кожна таблиця ініціалізації отримувала NAK у будь-якому режимі**.

Обидва драйвери тепер роблять канонічну SDK-послідовність: утримати PWDN+RESET через налаштування CSI → відпустити PWDN → 31 мс на стабілізацію живлення → відпустити RESET → запустити MCLK. Просто оновіться до v0.60.2 або новішої (внесок @tipoman9, перевірено на SSC378QE + IMX335).
:::

::: details CV610: камера «мертва» після падіння демона, або пропало аудіо
На CV610 стан MPP — це стан ядра, тож він переживає падіння процесу. Кілька правил, здобутих вимірюваннями у v0.65.7–v0.65.10:

- **Ніколи не вивантажуйте MPP-модулі під живим споживачем.** Саме через це прибрали дію `S95waybeam reload` і відкат модулів при невдалому старті. Правильне відновлення — `restart`.
- Рядки `MMB LEAK` у логах — це **ядро, що звільняє пам'ять**, а не втрата.
- `SIGKILL` лишає по собі не VB, а **стан ISP**, і додатково «підвішує» два блоки `aenc` — через що аудіо після падіння мовчки не піднімалося. З v0.65.9 `cv610_audio_start()` спершу циклює аудіо-модуль, тож звук повертається сам.
- OSD-регіон (RGN) від waybeam-hub **не переживає перезапуск venc** — його треба переставити.
:::

::: details Кодек H.264 не працює
Waybeam кодує **тільки H.265 (HEVC)** на обох чіпах. Поля `video0.codec` немає; H.264 не підтримується. Переконайтеся, що ваш приймач (PixelPilot, ffplay, QGroundControl, GStreamer) налаштований на H.265.
:::
