# Веб-панель та HTTP API

Waybeam включає вбудовану веб-панель та повний HTTP API для керування параметрами в реальному часі. Веб-панель доступна за адресою `http://<ip-камери>/` (порт за замовчуванням — 80) або просто `http://waybeam.local` — камера анонсує себе через mDNS. Довідник звірено з версією **v0.73.3** (кінець серпня 2026), контракт API — **0.22.0**.

---

### Веб-панель

<strong>Вкладка Settings (Налаштування)</strong>

Поля конфігурації згруповані за **13 вбудованими секціями**:

| Секція | Опис |
| :--- | :--- |
| System | Порт, розгін, логування |
| Sensor | Вибір сенсора (index / mode) |
| ISP | Експозиція (стелі й підлоги підсилення/витримки), AWB, AE-движок |
| Image | Дзеркало, фліп, поворот |
| Video | Бітрейт, FPS, GOP, QP-межі, `sliceCount`, framing, resilience |
| Outgoing | Стрімінг, адреса, режим |
| Discovery | mDNS-анонс у мережі (`waybeam.local`) |
| Audio | Кодек, частота, гучність |
| FPV | ROI-кодування + 3DNR |
| IMU | Гіроскоп BMI270 |
| Attitude | Штучний горизонт: roll/pitch/yaw з IMU, кути монтажу, трими рівня |
| Detection | NPU-детектор об'єктів: плагін, модель, пороги, OSD-рамки |
| Recording | Запис на SD-картку |

Понад ці 13 дешборд домальовує групи, які приходять **прямо з `/api/v1/capabilities`**, без жодного рядка в `dashboard.html`: **Snapshot** (`snapshot.enabled`, `quality`, `width`, `height`) і **QR** (`qr.tapEnabled`, `tapWidth`, `tapHeight`, `windowMs`) — разом із підказками. Через це на кожному чипі видно рівно ті контролі, які цей бекенд справді обслуговує.

**Елементи інтерфейсу:**

- 🟢 **Live** — параметр змінюється миттєво без перезапуску
- 🟠 **Restart** — потребує reinit пайплайну (автоматично)
- 🔴 **Reboot** — потребує повного перезавантаження камери (лише `video0.resilience`)
- **Apply Changes** — застосувати всі змінені поля
- **Save & Restart** — застосувати та перезапустити пайплайн
- **Restore Defaults** — повернути конфігурацію з диска

::: details Для версій до v0.8 — секція EIS (GyroGlide)
У старих версіях була окрема секція `eis` (гіроскопна стабілізація GyroGlide). Її **видалено у v0.8.0**. Стабілізація тепер живе у секції Video — поле `video0.framing` (див. [нижче](#framing-стабілізація-та-цифровий-зум)).
:::

::: details Для версій до v0.40 — 13 секцій, без Attitude
Секція **Attitude** (живі roll/pitch/yaw і кнопка «Capture level trims») з'явилась у WebUI у **v0.40**. У версіях 0.24–0.39 секцій було 13, а гіроскоп BMI270 значився у WebUI як POC без споживача.
:::

::: details Для версій до v0.48/v0.60 — без секцій Detection, Snapshot і QR
- **Detection** з'явилася у **v0.48.0** разом із самим NPU-детектором.
- **Snapshot** — картка, додана у **v0.60.0**, коли QR-захоплення перевели з PGM на MJPEG-канал.
- **QR** — група для luma-тапу (`qr.*`), додана у **v0.64.0**.
- У **v0.49.0** ненадовго з'явилася група **Frame size caps** (`video0.maxIBytes` / `maxPBytes`) — у v0.72.0 вона зникла разом із самими полями.
- Секції **Adaptive Encoder Control** і **Debug** окремими більше не рендеряться: поля детекції сцен живуть у Video, а `debug.showOsd` — серед системних.
:::

::: tip Власний дашборд
Вбудований веб-інтерфейс можна замінити, поклавши власні файли в `/usr/share/www` — вони мають пріоритет над вбудованим дашбордом.
:::

<strong>Вкладка API Reference</strong>

Документація всіх HTTP-ендпоінтів з прикладами відповідей. Категорії: Configuration, Encoder Control, ISP & Image Quality, Recording, Dual-Stream.

<strong>Вкладка Image Quality (ISP)</strong>

Прямий доступ до 62 параметрів ISP SigmaStar:

- **Параметри** — розгортувані секції з чіпами параметрів
- **Мульти-поля** — вбудований редактор для складних параметрів (colortrans, OBC, demosaic тощо)
- **Export / Import** — збереження та відновлення ISP-профілів у JSON

::: info IQ на CV610 — інша схема <Badge type="tip" text="v0.65.5+" />
CV610 теж обслуговує `/api/v1/iq` та `/api/v1/iq/set`, але **у власній формі відповіді** й із власним набором: **11 ISP-груп, 59 полів** — saturation, color_tone, шумозаглушення, різкість, гамма, експозиція тощо. Запис у поле сам обирає ту половину блока, у якій воно живе. Групи DRC і dehaze зареєстровані, але **обійдені (bypass)**.

`/api/v1/iq/import` на CV610 повертає `501` (у `capabilities` це видно як `routes.iq_import: false`). Сама вкладка IQ у дешборді з v0.65.5 керується capability-фідом, а не жорстко зашитою умовою — тому на CV610 вона більше не прихована.
:::

### HTTP API — довідник

Всі ендпоінти використовують HTTP GET (сумісно з BusyBox wget). Відповіді — JSON у форматі `{"ok": true/false, ...}`.

::: tip Три рівні мутабельності
- **live** — застосовується миттєво без переривання потоку
- **restart_required** — ініціює автоматичний reinit пайплайну
- **reboot** — потребує повного перезавантаження камери (лише `video0.resilience`)

`/api/v1/capabilities` показує рівень мутабельності та підтримку кожного поля бекендом.
:::

---

<strong>GET /api/v1/version</strong>

Повертає інформацію про версію.

```bash
curl http://<ip>/api/v1/version
```

**Відповідь:**
```json
{
  "ok": true,
  "data": {
    "app_version": "0.73.3",
    "backend": "star6e",
    "contract_version": "0.22.0",
    "config_schema_version": "0.22.0"
  }
}
```

Поле `backend` тепер має три можливі значення: `star6e`, `maruko` і **`cv610`**.

Значення `contract_version` / `config_schema_version` зростають з релізами. Ключові позначки, за якими варто орієнтуватись у скриптах:

| Контракт | Що змінилось |
| :--- | :--- |
| `0.11.0` | видалено `video0.frameLost` |
| `0.12.0` | attitude-API |
| `0.13.0` | новий ендпоінт `/api/v1/live/set` |
| `0.14.0` / `0.15.0` | гаряча заміна моделі детектора; детектор доїхав до Maruko (SCL port 3) |
| `0.16.0` | **breaking** — `/api/v1/snapshot.pgm` видалено (тепер `404`) |
| `0.18.x` | серія CV610: керування, вибір режиму сенсора, `video0.size`, IQ, QP-межі, resilience і слайси |
| `0.19.0` | **breaking** — прибрано `outgoing.shmThrottle`, recovery-IDR при повному кільці; заголовок frame-shm-кільця → v2 |
| `0.20.0` | snapshot і запис доїхали до CV610 |
| `0.21.0` | **breaking** — видалено `video0.maxIBytes` / `maxPBytes` |
| `0.22.0` | поточна: QP-межі на Maruko, `video0.intraRefreshQp` на CV610 |

::: warning `0.18.7` ніколи не існував як версія контракту
Її оформили під час рев'ю і влили у `0.19.0`. Жоден пристрій не повідомляє `contract_version: 0.18.7` — не звіряйтесь із нею у клієнтському коді.
:::

<strong>GET /api/v1/config</strong> — повна активна конфігурація.

<strong>GET /api/v1/capabilities</strong> — мутабельність кожного поля (`live` / `restart_required`) та підтримка бекендом.

```bash
curl http://<ip>/api/v1/config
curl http://<ip>/api/v1/capabilities
```

::: tip Перевірка підтримки
Підтримка полів залежить від бекенда. Наприклад, Star6E повертає `video0.scene_threshold` як підтримуване, а Maruko — ні. Використовуйте `capabilities` перед записом.
:::

<strong>GET /api/v1/modes</strong>

Перелік режимів сенсора (pad + роздільність) — поточний вибір і всі режими, які перелічує SDK. Заповнює випадайку в WebUI.

```bash
curl http://<ip>/api/v1/modes
```

::: warning Індекси sensor.mode перенумеровано (v0.21–v0.34)
Лінійки режимів перебудовано на обох платформах: Maruko — у v0.21/v0.23, Star6E — у **v0.25–v0.34** (власні in-tree драйвери IMX335/IMX415). Star6E-лінійки тепер: IMX335 — 2560×1920@30/60, 2560×1440@90, 2176×1224@100, 1920×1080@120, `1600×900@144`; IMX415 — 5 видимих режимів від 4K@~33 до `1728×816@120`. Індекси `sensor.mode` при цьому **перенумеровано кілька разів**, а режимів стало менше, ніж у стокового драйвера: збережений у конфізі індекс поза новим діапазоном не дає waybeam стартувати. Після оновлення звіряйте старі конфіги зі списком `/api/v1/modes` або ставте `-1` (автовизначення).
:::

::: details Деталі перенумерації v0.21/v0.23 (Maruko)
Лінійки режимів на Maruko перероблено: IMX415 отримав non-binned 16:9 режими на 1485 Mbps (аж до `1920×1080@100`), IMX335 — лінійку «найкращий на кожен fps» (30/50/60/90/100) та ультранизьколатентний `1536×864@144` (v0.24).
:::

### Читання та запис полів

<strong>GET /api/v1/get?field_name</strong>

```bash
curl "http://<ip>/api/v1/get?video0.bitrate"
```

```json
{"ok": true, "data": {"field": "video0.bitrate", "value": 8192}}
```

<strong>GET /api/v1/set?field_name=value</strong>

Записати поле. Live-поля застосовуються миттєво. Restart-поля ініціюють reinit.

```bash
# Миттєва зміна бітрейту (live)
curl "http://<ip>/api/v1/set?video0.bitrate=4096"

# Мульти-зміна (тільки для live-полів)
curl "http://<ip>/api/v1/set?video0.bitrate=4096&system.verbose=true"

# Зміна роздільної здатності (restart — reinit пайплайну)
curl "http://<ip>/api/v1/set?video0.size=1280x720"
```

**Відповіді:**
```json
// Одне поле
{"ok": true, "data": {"field": "video0.bitrate", "value": 4096}}

// Мульти-зміна
{"ok": true, "data": {"applied": [
  {"field": "video0.bitrate", "value": 4096},
  {"field": "system.verbose", "value": true}
]}}

// Restart-поле
{"ok": true, "data": {"field": "video0.size", "value": "1280x720", "reinit_pending": true}}
```

::: warning Обмеження мульти-set
Мульти-set підтримується тільки для live-полів. Якщо хоча б одне restart-поле присутнє — весь запит відхиляється. Restart-зміни відправляйте по одній (демон перезапускається між ними — чекайте, поки відновиться).
:::

::: danger HTTP 409 — помилка валідації
Якщо значення невалідне (наприклад, неіснуючий режим AWB або неіснуюче поле), API поверне **HTTP 409 Conflict** замість 200.

З **v0.64.0** сюди ж потрапив і невідомий пресет `video0.resilience`. Раніше такий запит повертав **200**, зберігав хибну назву у `/etc/waybeam.json` і лишав похідні поля (`intra_refresh_*` / `ref_*`) із розгорткою **попереднього** пресету — тож `/api/v1/config` розходився з реальним енкодером аж до наступного старту, де завантажувач із диска відкочувався на `"off"`, і оператор опинявся на пресеті, якого не просив.
:::

<strong>GET /api/v1/live/set?field_name=value</strong> <Badge type="tip" text="v0.50+" />

Те саме, що `/set`, але **без запису на флеш**: значення застосовується лише до активної конфігурації в пам'яті.

```bash
curl "http://<ip>/api/v1/live/set?video0.bitrate=4096"
```

Створений для високочастотних автоматичних записувачів — адаптивного бітрейту, кадрових обмежень і fps-актуації waybeam-link. Персистувати з такою частотою погано двічі: зношується флеш, і камера завантажується в останній адаптивний «перехідний» стан.

- **Тільки live-поля.** Restart-класове поле повертає `400` («restart-class field requires persistence; use /api/v1/set») — reinit пайплайну перечитує конфіг із диска і мовчки викинув би це значення.
- Форми відповіді **байт-у-байт** такі самі, як у `/set`. Підтримуються і одиночний, і мульти-set.
- Пізніший персистуючий `/set` чи `/defaults` знімає знімок **усього** поточного стану, включно з волатильними змінами (конфіг один — так задумано).
- Збірки без цього ендпоінта повертають `404`: клієнт пробує один раз і відкочується на `/set`. Саме так робить waybeam-link.

<strong>GET /api/v1/restart</strong>

Повний reinit пайплайну. Перезавантажує `/etc/waybeam.json` та перезапускає камеру без завершення процесу.

```bash
curl http://<ip>/api/v1/restart
```

### Контроль енкодера

<strong>GET /request/idr</strong>

Запит IDR-кейфрейму від енкодера:

```bash
curl http://<ip>/request/idr
```

::: tip Коли запитувати IDR
- Після підключення нового глядача
- Після втрати пакетів у радіоканалі
- При появі артефактів відео
:::

<strong>GET /api/v1/idr/stats</strong>

Лічильники rate-limit IDR за каналом: скільки запитів виконано, а скільки злито (coalesced).

<strong>GET /api/v1/awb</strong>

Стан автобалансу білого від ISP. З **v0.68.2** працює і на CV610.

<strong>GET /api/v1/ae</strong>

Стан автоекспозиції разом із `runtime.active_precrop` (обидва SigmaStar-бекенди).

<strong>GET /api/v1/intra/status</strong> та <strong>GET /api/v1/resilience/status</strong>

Живий стан intra-refresh (rolling GDR) та обраного resilience-пресету — саме те, що реально стоїть в енкодері, а не те, що записано в конфізі. Обслуговувалися вже кілька релізів, але в контракт потрапили лише у **0.18.6**; з появою CV610-гілки (0.18.5) віддають реальний стан пристрою.

<strong>GET /api/v1/fps/config</strong> та <strong>GET /api/v1/fps/live</strong>

Сконфігурована та фактично доставлена частота кадрів.

```bash
curl http://<ip>/api/v1/idr/stats
curl http://<ip>/api/v1/awb
curl http://<ip>/api/v1/resilience/status
curl http://<ip>/api/v1/fps/live
```

::: info Записи rate-control більше не форсують IDR <Badge type="warning" text="v0.69+" />
`video0.bitrate` і `video0.qpDelta` більше **не просять IDR** після застосування (Star6E та Maruko; CV610 ніколи цього й не робив). Заміряно на SSC338Q 23 серпня: десять живих записів із інтервалом 300 мс, підрахунок IRAP просто у бітстрімі енкодера — `qpDelta` впав з 11 IDR до 1.

Шлях `bitrate` **на ефірі** не змінився, бо `MI_VENC_SetChnAttr` сам по собі емітить IDR, а в `MI_VENC_RcParam_t` немає поля бітрейту, тож перемикатися нема на що. Але виправлення дало інше: запис бітрейту більше не «з'їдає» спільний 100-мілісекундний шлюз IDR (справжній запит на відновлення, що приходив у це вікно, просто ковтався), і `/api/v1/idr/stats` більше не рахує IDR на кожен запис бітрейту, якого той запис не спричиняв.

Bootstrap-IDR (увімкнення виходу, зміна призначення, live-rebind fps, старт запису) **проходить повз шлюз безумовно** — приймач, який ще не бачив parameter set, не має з чого стартувати. Вони й далі рахуються у `/api/v1/idr/stats` і переозброюють вікно.
:::

### Спостереження за потоком

<strong>GET /api/v1/transport/status</strong>

Стан активного відеотранспорту. Набір полів **різний для трьох типів транспорту**:

| Транспорт | Поля |
| :--- | :--- |
| `frame-shm://` | поля кільця + `ringLowWaterSlots`, `otherDrops` |
| `shm://` | поля кільця пакетів |
| UDP / Unix | підмножина сокетних полів + `transportDrops` / `packetsSent` |

`badAuDrops` присутній на кожному транспорті (на CV610 — ні: у його шляху потоку немає валідації таблиці пакетів).

::: warning Змінені поля у v0.69.0 <Badge type="danger" text="BREAKING" />
`throttlePermille` та `effectiveBitrateKbps` **видалено** разом із самим механізмом клампа. Натомість на гілці `frame-shm` з'явився `ringLowWaterSlots` — і **полярність інвертована**: тут здоровим є **низьке** число (`<= 1`), тоді як для клампа здоровим було `1000`. Бітрейт читайте просто з `/api/v1/config` → `video0.bitrate`: «ефективної» масштабованої величини більше немає, бо її більше ніщо не масштабує.

Також з'явився `otherDrops` — кадри, які producer відкинув **не** через повне кільце (завеликий або пошкоджений access unit). Раніше публікувався лише `full_drops`, тож споживач був структурно сліпий до таких втрат: кадр просто зникав. Розділені навмисно — ці дві ситуації вимагають від регулятора швидкості протилежної реакції.
:::

<strong>GET /api/v1/audio/status</strong>

Знімок аудіо-пайплайну: чи завантажена бібліотека, стан захоплення, кодек, частота, канали, ініціалізація Opus. На CV610 реалізовано з **v0.65.1** (раніше повертав `501`, хоча аудіо працювало).

```bash
curl http://<ip>/api/v1/transport/status
curl http://<ip>/api/v1/audio/status
```

### Attitude: штучний горизонт з IMU

З **v0.39–v0.40** Waybeam оцінює орієнтацію камери (roll/pitch/yaw) за даними гіроскопа BMI270 — для штучного горизонту в HUD наземної станції. Потрібно `imu.enabled=true` та `attitude.enabled=true` (обидва — restart).

<strong>GET /api/v1/attitude</strong> — живий знімок кутів (у системі координат камери, з урахуванням монтажних тримів):

```bash
curl http://<ip>/api/v1/attitude
```

<strong>GET /api/v1/attitude/calibrate_level</strong> — калібрування рівня однією командою: тримайте камеру нерухомо і рівно ~1.5 с — сервіс усереднить акселерометр, точно обчислить трими (`attitude.trimRollDeg` / `trimPitchDeg`), збереже їх у конфіг і перезапустить пайплайн:

```bash
curl http://<ip>/api/v1/attitude/calibrate_level
```

Можливі помилки: **409** — IMU вимкнений або камера рухається; **501** — на Maruko (оцінювач ще не підключений до IMU-шляху цього бекенда).

Поля секції `attitude` (усі — restart):

| Поле | Опис |
| :--- | :--- |
| `enabled` | Увімкнути оцінку горизонту |
| `mountDeg` | Кут монтажу камери навколо осі об'єктива: 0 / 90 / 180 / 270 |
| `invertRoll` / `invertPitch` | Інверсія знаків кутів |
| `axisFwd` / `axisDown` | Перестановка осей сенсора для плат у нестандартній орієнтації (будь-яка з 24 осьових); за замовчуванням `+x` / `+z` |
| `trimRollDeg` / `trimPitchDeg` | Трими рівня — їх записує калібрування |

::: info ATTITUDE у RTP-sidecar
За увімкненого sidecar (`outgoing.sidecarPort`) до покадрової телеметрії додається 12-байтовий трейлер **ATTITUDE** (roll/pitch/yaw у кроках 0.1°, статус, вік IMU-семплу) — для HUD. Сам sidecar з v0.39 **мультипідписний**: до 4 одержувачів одночасно (TTL 5 с на слот), тож підписка HUD більше не «викрадає» телеметрію у wfb-контролера. Трейлер — тільки Star6E. З v0.40.1 оцінювач відкидає биті IMU-семпли (NaN/Inf) і не публікує «застиглий» горизонт.
:::

У WebUI секція **Attitude** показує кути наживо (опитування 1 Гц) і має кнопку **Capture level trims** — калібрує, оновлює поля та перезапускає пайплайн.

### Discovery (mDNS)

Камера анонсує себе в локальній мережі як сервіс `_waybeam-venc._tcp.local`: унікальне ім'я `waybeam-<суфікс>.local` (суфікс — хвіст die ID чипа SigmaStar) та, за замовчуванням, коротке `waybeam.local`. Поля секції `discovery` доступні через API та WebUI (секція Discovery):

```bash
# Стан анонсу
curl "http://<ip>/api/v1/get?discovery.enabled"

# Власне ім'я замість waybeam-<суфікс>
curl "http://<ip>/api/v1/set?discovery.name=my-drone"

# Вимкнути коротке ім'я waybeam.local (корисно, якщо камер у мережі кілька)
curl "http://<ip>/api/v1/set?discovery.bareAlias=false"
```

Повний 12-значний серійник (die ID) — у `GET /api/v1/config` → `data.device.serial` (тільки читання). Конфлікт короткого імені між кількома камерами вирішується автоматично за RFC 6762 (IP-tiebreak).

### Snapshot (JPEG)

<strong>GET /api/v1/snapshot.jpg</strong>

Один JPEG-кадр з окремого MJPEG-каналу VENC (відгалуження від того ж порту, що й основний H.265-потік). Без параметрів; якість за замовчуванням 80, роздільність — як в основному потоці.

```bash
curl -o snapshot.jpg http://<ip>/api/v1/snapshot.jpg
```

Відповідь — `Content-Type: image/jpeg`. Можливі помилки: `503 snapshot_disabled` (пайплайн ще не піднявся), `504 snapshot_timeout` (немає кадру за 1500 мс), `500 snapshot_failed`.

::: info Налаштування snapshot
`snapshot.quality` — **live** (миттєво, без reinit). Поля `snapshot.channel`, `snapshot.width`, `snapshot.height` — restart (зашиваються при `MI_VENC_CreateChn`). `width=0`/`height=0` означає «як в основному потоці».

З **v0.70.0** `/api/v1/snapshot.jpg` працює і на **CV610** — це був останній маршрут, якого бекенду бракувало.
:::

::: details Для версій до v0.60 — ендпоінт `/api/v1/snapshot.pgm` <Badge type="danger" text="ВИДАЛЕНО" />
Раніше існував сірий PGM-знімок `/api/v1/snapshot.pgm`, яким користувався QR-декодер. У **v0.60.0** його **видалено — тепер він повертає `404`**, і це не «прибирання зайвого»: його VPE/SCL-тап, що створювався на кожен запит, **міг підвісити SoC**. Заміряно на пристрої: `DisablePort … mhal not return buffer` → шторм `EnsureInputPortFifoEmpty`.

QR-сканування тепер споживає звичайний `GET /api/v1/snapshot.jpg`, а `qr_decode` читає JPEG нативно (і збирається з `-O3` — у 1.66× швидше наскрізь). Разом із ендпоінтом зникли коди помилок `bad_crop`, `bad_max_dim`, `snapshot_gray_busy` і `snapshot_gray_unsupported`.
:::

### Детекція об'єктів на NPU <Badge type="tip" text="v0.48+ · Star6E, Maruko" />

Waybeam запускає детектор об'єктів на **простоюючому IPU/NPU** камери. Архітектура плагінна: модель живе в окремому `.so`, тож нова модель = зміна конфіга, без перезбирання waybeam. Результат іде як **DETECT-трейлер у RTP-sidecar** (флаг `0x10`, до кожного кадру) і як рамки на debug-OSD.

Живі поля — вмикання, гаряча заміна моделі без розриву потоку, пороги:

```bash
curl "http://<ip>/api/v1/set?detect.enabled=true"
curl "http://<ip>/api/v1/set?detect.modelPath=/opt/models/sar_person.img"
```

::: warning `detect` і `framing=stab` взаємовиключні
Обидва претендують на один тап (VPE port1 на Star6E, SCL port3 на Maruko). На CV610 детекції немає.
:::

→ **[Повний довідник: детекція об'єктів на NPU](/software/waybeam-detection)** — усі поля `detect`, формат трейлера, геометрія тапу, `modelId`, історія та обмеження.

### QR-сканування на борту <Badge type="tip" text="v0.60+ · Star6E" />

Камера декодує QR-маркер із власного кадру через luma-тап **без накладеного OSD**. Ендпоінти: `GET /api/v1/qr/scan[?ms=N]` (вікно, що само закривається на знайденому коді), `/qr/stop`, `/qr/status`, `/qr/tap.pgm`.

```bash
curl "http://<ip>/api/v1/qr/scan?ms=10000"
curl "http://<ip>/api/v1/qr/status"    # payload у data.decode.payload
```

::: danger Парування як таке ще НЕ реалізоване
Waybeam постачає лише транспортний шар: повертає 16 символів і зупиняється — **не інтерпретує, не авторизує, не зберігає й не виконує** цей payload. Префікси `P`/`C` зарезервовано під майбутню логіку парування та команд, але вона свідомо винесена за межі бінарника waybeam.
:::

→ **[Повний довідник: QR-сканування на борту](/software/waybeam-qr)** — формат маркера, бюджет пікселів на модуль, генерація, усі відповіді API та пріоритети на port1.

### Запис на SD-картку

<strong>GET /api/v1/record/start</strong>

Почати запис. Використовує сконфігурований `record.dir`, або вкажіть каталог параметром:

```bash
curl "http://<ip>/api/v1/record/start"
curl "http://<ip>/api/v1/record/start?dir=/mnt/mmcblk0p1"
```

<strong>GET /api/v1/record/stop</strong> — зупинити запис.

<strong>GET /api/v1/record/status</strong> — статус запису:

```bash
curl "http://<ip>/api/v1/record/status"
```

```json
{
  "ok": true,
  "data": {
    "active": true,
    "format": "ts",
    "path": "/mnt/mmcblk0p1/rec_01h23m45s_abcd.ts",
    "frames": 1500,
    "bytes": 12345678,
    "segments": 1,
    "elapsed_ms": 25000,
    "droppedFrames": 0,
    "writerPeakDepth": 1,
    "stop_reason": "none"
  }
}
```

<strong>GET /api/v1/recordings</strong> — перелік файлів у `record.dir`; <strong>/recordings/download</strong> і <strong>/recordings/delete</strong> — завантажити та видалити. Працюють на обох SigmaStar-бекендах незалежно від того, який із них писав файл.

::: tip Запис працює на всіх трьох чіпах <Badge type="tip" text="виправлено" />
Раніше і документація, і сам контракт стверджували, що HTTP-керування записом — Star6E-only, а Maruko повертає `501`. Це було **застаріле твердження**: Maruko опитує ті самі прапорці старту/зупинки, відколи зареєстрував `record_http_control_supported(true)`. У контракті **0.22.0** рядок виправлено.

**CV610** отримав запис у **v0.70.0** — у режимі `record.mode: "mirror"`, формат `ts` із мукшеним Opus. Режими `dual` / `dual-stream` там потребують другого VENC-каналу, тож запит відхиляється з попередженням, а не пише мовчки канал 0.
:::

::: warning Запис більше не гальмує ефір <Badge type="tip" text="v0.70+" />
До v0.70 **кожен бекенд викликав рекордер прямо з циклу кодування**: `write()` на SD-карту стопорив шлях живого відео. Тепер запис виконується у **власному потоці** на всіх трьох бекендах (кількість потоків 8 → 9 під час запису), а `writerPeakDepth` у статусі показує глибину черги під час ротації.

Заодно виправлено те, що ротація за `record.maxSeconds` / `maxMB` **була інертною на GDR-крафті**: ротація вимагає точки входу в потік, а GDR-стрім не має природних IDR — тепер ротація сама просить IRAP.

Далі серія фіксів 0.73.1–0.73.3: `/record/status` більше не читає стан рекордера навперейми з потоком запису (тепер це узгоджений знімок), `record/stop` посеред запису більше не може застопорити живе відео, а `record.mode=dual` на Maruko більше не б'є стек власного потоку і не форсує кейфрейм у **живий** потік.
:::

::: info Точний сенс `droppedFrames` <Badge type="tip" text="контракт 0.20.1" />
Лічильник рахує **кожен кадр запису, що не дійшов до файлу**, а не лише ті, які відхилила черга: access unit із неповною таблицею `packetInfo` або більший за байтову межу черги взагалі до черги не доходив, і рахувати тільки відмови черги означало пропускати їх мовчки.

`droppedFrames` і `writerPeakDepth` — **на кожен запис, а не на процес**. Раніше writer на SigmaStar переживав будь-який окремий запис, і обидва лічильники накопичувались за весь час життя демона: чистий запис показував втрати попереднього, а один загублений кадр «отруював» кожен наступний запис.
:::

### Framing: стабілізація та цифровий зум

`video0.framing` — це **єдиний користувацький перемикач** обрізки VPE. Це іменований пресет (restart-required); коефіцієнт обрізки *виводиться* з пресету (окремого поля `zoomPct` немає).

| `framing` | Ефект | Роздільність @1080p | Чіпи |
| :--- | :--- | :--- | :--- |
| `off` | Повний кадр | 1920×1080 | обидва |
| `stab` | Стабілізація (центрована обрізка 80%) | 1536×864 | обидва (Maruko — з v0.35) |
| `stab-fill` | Стабілізація (плаваюче зображення на чорній рамці) | 1920×1080 | обидва (Maruko — з v0.37) |
| `zoom-1.25x` | Цифровий зум 1.25× | 1536×864 | обидва |
| `zoom-1.50x` | Цифровий зум 1.50× | 1280×720 | обидва |
| `zoom-1.75x` | Цифровий зум 1.75× | 1088×608 | обидва |
| `zoom-2x` | Цифровий зум 2× | 960×528 | обидва |
| `zoom-3x` | Цифровий зум 3× | 640×352 | обидва |
| `zoom-4x` | Цифровий зум 4× | 480×256 | обидва |

::: info «Обидва» означає SigmaStar
На **CV610** поля `video0.framing` немає взагалі — ні стабілізації, ні цифрового зуму. Перевіряйте через `/api/v1/capabilities`.
:::

**Цифровий зум** зменшує і вікно обрізки, і вихідну роздільність — без апскейлу, без додаткового навантаження на канал. Панорамування всередині зуму — live, через `video0.zoomX` / `video0.zoomY` (∈ [0,1], центр 0.5/0.5):

```bash
# Увімкнути 3× зум (restart)
curl "http://<ip>/api/v1/set?video0.framing=zoom-3x"

# Панорамування (live) — лівий верхній кут / центр
curl "http://<ip>/api/v1/set?video0.zoomX=0.0&video0.zoomY=0.0"
curl "http://<ip>/api/v1/set?video0.zoomX=0.5&video0.zoomY=0.5"
```

**Стабілізація** (`stab` / `stab-fill`) використовує Kalman-фільтр траєкторії і з v0.35/v0.37 працює на обох чіпах. Тонке налаштування (всі restart; повторний вибір пресету скидає їх до дефолтів, тому **спочатку задавайте `framing`, потім переоприділення**):

| Поле | За замовч. | Опис |
| :--- | :--- | :--- |
| `video0.stabAccuracy` | `auto` | Рівень детектора руху: `high` / `medium` / `low` (якість ↔ CPU). `auto` = `high` на Star6E, `low` на одноядерному Maruko (v0.36) |
| `video0.stabCropPct` | 80 | Запас на стабілізацію (менше = більший «мертвий» бордер, більше поглинання руху) |
| `video0.stabKalmanQ` | 0.03 | Реакція на панорамування (`0.001..1.0`; вище = швидше слідує за повільними панорамами) |
| `video0.stabKalmanR` | 2.0 | **Головний параметр відчуття.** Плавність (`0.1..50.0`; вище = плавніше, але із затримкою) |
| `video0.pauseStab` | — | **live** пауза: плавно повертає вікно/зображення в центр (тільки `stab`/`stab-fill`) |

::: warning Стабілізація на Maruko — ціна CPU
Детектор руху — програмна NEON-бібліотека SigmaStar, не апаратний блок. На одноядерному Maruko це помітна частка CPU (у `stab-fill` ≈29% ядра на 50 fps при `stabAccuracy=low`). Також на Maruko `stab-fill` несумісний з `record.mode: "dual"` — такий запит відхиляється.
:::

::: details Для версій до v0.35/v0.37 — стабілізація лише на Star6E
До v0.35 `stab`, а до v0.37 і `stab-fill` працювали тільки на Star6E: на Maruko детектор `MI_IVE` не ініціалізувався через несумісну vendor-бібліотеку, тож WebUI показував контролі стабілізації неактивними, а `/set` відхиляв відповідні поля. З v0.35 тарбол Maruko постачає сумісну `libmi_ive.so`, і обидва пресети доступні на обох чіпах.
:::

```bash
# Увімкнути стабілізацію (restart)
curl "http://<ip>/api/v1/set?video0.framing=stab"

# Пауза стабілізації на льоту (live)
curl "http://<ip>/api/v1/set?video0.pauseStab=1"   # заморозити (плавно в центр)
curl "http://<ip>/api/v1/set?video0.pauseStab=0"   # відновити
```

::: info Стабілізація не використовує гіроскоп
Стабілізація працює на основі аналізу руху в кадрі (Kalman) і **не використовує IMU**. Колишня EIS на BMI270 (`gyroglide`) видалена у 0.8.0. Сам гіроскоп з v0.39 живить іншу функцію — [оцінку горизонту (attitude)](#attitude-штучний-горизонт-з-imu).
:::

### Resilience: стійкість до втрат пакетів

`video0.resilience` обирає профіль стійкості — intra-refresh (rolling GDR-смуга), SVC-T пірамида посилань та довжина GOP виводяться з пресету.

::: danger Зміна resilience потребує REBOOT
Запис `video0.resilience` зберігає значення у `/etc/waybeam.json` і повертає `{"reboot_required": true}`. **Активний пайплайн продовжує працювати зі старим пресетом до наступного запуску камери** — kernel-модуль SigmaStar MI не переживає live-переконфігурацію цих полів (на Star6E це призводить до kernel panic, на Maruko — до зависання демона). Тому застосовується модель «cold-boot».
:::

| Пресет | intra-refresh | refPred | GOP | OSD-safe? |
| :--- | :--- | :--- | :--- | :--- |
| `off` | вимк. | вимк. | користувацький | так |
| `rescue` | вимк. | вимк. | 0.25 с (IDR-спам) | так |
| `quality` | вимк. | вимк. | 4.0 с | так |
| `sprint` | швидкий (150 мс) | вимк. | 0.5 с | так |
| `racing` | швидкий (150 мс) | вимк. | 2.0 с | так |
| `endurance` | збалансований (500 мс) | вимк. | 2.0 с | так |
| `patrol` | збалансований (500 мс) | вимк. | 4.0 с | так |
| `rally` | швидкий (150 мс) | base=1, enhance=1 | 2.0 с | ні — «зелений шлейф» |
| `range` | збалансований (500 мс) | base=1, enhance=4 | 2.0 с | ні — «зелений шлейф» |
| `fpv` | стійкий (1000 мс) | base=1, enhance=4 | 2.0 с | ні — «зелений шлейф» |
| **`ltr`** / `ltr:<N>` | **вимк. (примусово)** | enhance=N (типово 1) | **ваш `gopSize`** | ні — «зелений шлейф» |

<strong>Пресет `ltr`</strong> <Badge type="tip" text="v0.64+" />

Найстійкіша структура посилань, яку цей SoC узагалі здатен виразити: `InRnRnRn…` — **половина кадрів нереференсні**, тож половина всіх втрат коштує рівно один кадр замість каскаду до наступного IDR. На відміну від `rally` (те саме співвідношення 1:1), `ltr` **зберігає ваш `gopSize`** і примусово вимикає intra-refresh — тож його можна поєднувати з довгим GOP та асиметричним FEC у транспорті: важкий захист на IDR, легкий на решті.

Семантику `MI_VENC_ParamRef_t.u32Enhance` довелося встановлювати **вимірюванням** (SDK не документує нічого): це **період** — рівно один кадр із кожних `enhance + 1` виходить нереференсним. Заміряно: `enhance=1` → 50.0% скидних, `4` → 17.6%, `299` → 0.3%. Тобто **менше значення — стійкіше**: голий `ltr` використовує 1, а `ltr:<N>` тим менш стійкий, чим більший N.

Ціна за бітрейтом при закріпленому QP 30 на рухомій сцені — **менше 1%** відносно `off` (5.62/5.64 проти 5.65/5.68 Мбіт/с у чергуванні запусків).

::: info Що ще з'ясувалося при вимірюванні
P-кадри **завжди** передбачають із попереднього кадру, ніколи з IDR (розмір кадру рівний по всьому GOP під рухом), а `bEnablePred` для позначення нереференсних кадрів — **no-op**: `rally` (`pred=true`) і `ltr:1` (`pred=false`) дають ідентичні патерни. Повний SDK SigmaStar не має жодного API для long-term reference, SmartP чи GOP-mode — тож структура з «віртуальним IDR» на Infinity6E недосяжна.
:::

```bash
# FPV з OSD-оверлеєм — швидке відновлення смугами, без SVC-T
curl "http://<ip>/api/v1/set?video0.resilience=racing"

# Максимальна стійкість при довгому GOP + асиметричний FEC
curl "http://<ip>/api/v1/set?video0.resilience=ltr"

# далі перезавантажте камеру, щоб застосувати
```

::: warning OSD та SVC-T
Пресети з `refPred` (`rally`, `range`, `fpv`, `ltr`) можуть лишати стійкий «зелений шлейф» на статичному OSD до наступного IDR — `ltr` максимізує цей ефект найсильніше. Для польотів з OSD-оверлеєм використовуйте OSD-safe пресети (`racing`, `endurance`, `patrol`). Бюджетуйте +20–30% бітрейту для пресетів з intra-refresh.
:::

### Багатослайсове H.265 (`video0.sliceCount`) <Badge type="tip" text="v0.66+" />

`video0.sliceCount` (1..32, за замовчуванням `1`, **restart**) ділить кожен кадр на кілька незалежних слайсів. Сенс — просторове приховування втрат: коли втрата в радіоканалі виходить за бюджет FEC, вона коштує **замерзлу ділянку**, а не весь кадр.

| Бекенд | З версії | Деталі |
| :--- | :--- | :--- |
| Star6E | v0.66.0 | `MI_VENC_SetH265SliceSplit` — символ експортувався бібліотекою весь час, але ніколи не був підключений. Запитує `ceil(rows/sliceCount)` CTU-рядків на слайс |
| CV610 | v0.67.0 | Розбиття по рядках LCU (32 пікселі), early slice output вимкнено |
| Maruko | v0.67.0 | Пов'язується device-aware ABI у вікні між `CreateChn` і `StartRecvPic` |

Реально доставлену кількість обмежує геометрія кадру. Перевірено на залізі: на CV610 (1080p30/60/100) запити 1, 3, 4, 6, 9, 12 і 17 дали точну кількість VCL-NAL; на Maruko 720p30 запити 1, 4 і 12 виконано точно, а 17 і 32 квантувалися до максимуму картинки — **12**.

Якщо явно запитано кілька слайсів, а ABI не вдається застосувати або зчитати назад — **старт падає з помилкою**, а не мовчки віддає однослайсовий потік. `sliceCount=1` лишається сумісним зі старими бібліотеками.

Публікація у frame-SHM не змінилася: як і раніше **один access unit на слот**, просто тепер із N слайс-NAL усередині.

::: details Для версій v0.66 — стеля у 8 слайсів
Перша реалізація (лише Star6E) мала обмеження `packetInfo[8]` і документувалась як «перевірена межа — 4 слайси». У **v0.67.0** з'ясувалося, що це було непорозуміння: `packetInfo[8]` — це **на один pack**, а кожен вихідний шлях і так обходить усі pack'и в access unit. Стелю знято, спільний діапазон запиту тепер 1..32, а реальну межу задає геометрія пристрою.
:::

### Rate control: QP-межі та `qpDelta`

| Поле | Мутабельність | Star6E | Maruko | CV610 |
| :--- | :--- | :--- | :--- | :--- |
| `video0.minQp` / `maxQp` | live | ✅ v0.64 | ✅ **v0.73.0** | ✅ v0.65.6 (P-межі + стеля I; підлога I не керується) |
| `video0.qpDelta` | live | ✅ дефолт **−12** | ✅ дефолт **−12** | ❌ прибрано у v0.73.0 |
| `video0.intraRefreshQp` | restart | ❌ | ❌ | ✅ v0.73.0 |

```bash
curl "http://<ip>/api/v1/set?video0.minQp=22&video0.maxQp=42"
```

::: warning Зміни дефолтів і поведінки у v0.73.0
- **`video0.qpDelta` мовчки відкочувався при старті** (#255): застосований зі стартового шляху venc, він **логував успіх, не доходячи до енкодера** — реально працював лише живий запис. Виправлено.
- **Дефолт `qpDelta` тепер `-12`** на Star6E і Maruko (був `0`) — щоб обмежити вартість IDR.
- **`qpDelta` прибрано з CV610**: його CBR-контролер зберігає значення, але не діє на нього. Замість нього там `video0.intraRefreshQp` — важіль QP для смуги intra-refresh.
- На Star6E запит `minQp > maxQp` тепер **відхиляється**, а не записується.
:::

### ISP Image Quality

<strong>GET /api/v1/iq</strong> — експорт усіх ISP-параметрів:

```bash
curl http://<ip>/api/v1/iq > my_tuning.json
```

<strong>POST /api/v1/iq/import</strong> — імпорт (повний або частковий):

```bash
# Повний імпорт
curl -X POST -H "Content-Type: application/json" \
  -d @my_tuning.json http://<ip>/api/v1/iq/import

# Частковий імпорт — тільки конкретні параметри
echo '{"lightness":{"value":75},"demosaic":{"fields":{"dir_thrd":30}}}' | \
  curl -X POST -H "Content-Type: application/json" -d @- http://<ip>/api/v1/iq/import
```

<strong>GET /api/v1/iq/set?param=value</strong> — зміна окремого ISP-параметра (dot-notation):

```bash
# Встановити одне поле
curl "http://<ip>/api/v1/iq/set?colortrans.y_ofst=200"

# Встановити масив (через кому)
curl "http://<ip>/api/v1/iq/set?colortrans.matrix=23,45,9,1005,987,56,56,977,1015"
```
